# Slice 41 — encrypted recovery and writable readiness

The production database image now includes pinned PostgreSQL 17/pgBackRest and a required private repository configuration. Production Compose enables WAL archiving and mounts the backup secret only in the database container. An explicit build context excludes private files. The S3 configuration template requires repository encryption, TLS verification and a 30-day recovery window. Host timer templates schedule weekly full/daily differential backups and five-minute archive/freshness checks; external alert delivery remains an operator deployment requirement.

The operations CLI exposes reviewed init/check/full/diff/status/verify/expiry-preview actions without printing secrets or raw command output. Status requires a successful archive check, encrypted healthy metadata, a full backup and a recent valid backup timestamp. A readable schema on a recovering or read-only database is no longer application readiness, preventing web/worker startup against an unfinished recovery target.

The disposable recovery runner creates the full schema and scored synthetic competition, takes an encrypted backup, commits a WAL-only marker and named recovery point, then commits a later excluded marker. It removes the original data volume. Wrong credentials and missing target WAL cannot yield a ready restored database. The intact repository restores into a new volume, preserves all 18 result payloads/checksums, includes the WAL-only marker, excludes the later marker, validates schema readiness and pauses provider traffic before restart. It loads no local environment credentials and makes no live provider or email calls.

Verification passed: strict build/types/lint, 120 unit/harness cases, 151 disposable PostgreSQL cases (10 persistence + 141 application), Compose validation, systemd calendar parsing and the encrypted recovery drill. The latest local drill took 37 seconds including the deliberate failed recovery waits; this is a small local dataset, not a production RPO/RTO measurement. Source-bound evidence is in artifacts/verification/recovery-proof.json. Required CI now also builds the backup image and runs the restore rehearsal.

No application database migration is required. Roll out the Debian database image initially on clean staging/production; existing Alpine volumes require separately reviewed collation/migration handling. Before opening production writes, configure the actual off-host repository, initialize/check it, take a full backup, verify status, install monitoring and complete a clean-host drill with the selected dataset and hardware.
