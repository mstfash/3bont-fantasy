# Slice 43 — cutoff contention and connection-loss recovery

The new disposable PostgreSQL rehearsal creates 100 synthetic accounts with 200 squads across two competitions sharing a season. Ordinary entry commands create every squad and activate 100 Bench Boost chips, producing 300 accepted receipts. Two parent locks hold 200 lineup requests that reach PostgreSQL before the deadline. The locks release after the authoritative cutoff; all 200 changes are rejected and the accepted-receipt count stays unchanged.

A controlled trigger pauses the actual deadline worker transaction after 25 snapshot inserts. Terminating only that rehearsal's named PostgreSQL backend proves the transaction leaves no snapshots, frozen player pool or locked status behind. Six competing recovery runs then lock the two rounds exactly once, producing 200 snapshots. Every resulting lineup, bank balance, transfer allowance and chip inventory matches one canonical transition. Replaying all original entry-creation commands after the cutoff returns their original receipts without creating entries or consuming chips again. Fixture cleanup removes the test's trigger and records even on failure.

The interruption exposed a real process-lifecycle issue. PostgreSQL connections can emit error events both while idle in a pool and while checked out between transaction queries. Handling only the pool's idle error event does not cover both cases. Web and worker now use a shared managed pool that observes both event sources with fixed, credential-free logs. Failed queries still reject their callers; the helper never retries writes or reports a failed transaction as committed. PostgreSQL removes failed connections, allowing later work to establish fresh ones. See the upstream [pool event documentation](https://node-postgres.com/apis/pool).

The container proof now stops and restarts its isolated PostgreSQL server. The production web reports unavailable during the outage, recovers in the same process and preserves both its authenticated session and database-backed rate limit. Disconnecting the worker's idle application connections does not restart its process; it completes another durable job afterward. The existing TLS, migration, secure-cookie, origin, header-spoofing and private-outage-log checks remain in that test.

Local verification passed: strict checks, 113 unit + nine harness cases, 152 PostgreSQL cases (10 persistence + 142 application), 56 public smoke combinations and authenticated Arabic/English E2E. Rebuilt web/worker containers passed the expanded connection-recovery checks. Evidence is recorded in artifacts/verification/deadline-contention-proof.json, tls-proof.json and container-proof.json. No database migration is required.

This is correctness and connection-recovery evidence with a small synthetic dataset. The full HTTP/browser workload, production-sized history, measured latency on named hardware, off-host disaster recovery and real production dependencies remain separate release gates.
